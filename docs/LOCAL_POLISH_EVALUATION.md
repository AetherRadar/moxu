# 本地末尾润色模型评估

评估日期：2026-09-19。模型来源：`/Users/imac/bookzd/sft_qwen3_1p7b_merged`，Qwen3 1.7B 合并权重，BF16。原始权重未修改。

## 结论

本次样本中，模型生成速度快，但内容保真不稳定。**按当前使用方案，墨序默认使用这个本地模型，并增加数字保护**：按上下文定位对应数字，能明确对应的恢复为原始数字与单位；遗漏、新增或无法确定对应关系时保留原选区。结果仍先显示差异，再由作者决定是否应用。通用模型可手动选择，不自动回退；没有继续使用旧的算法评分、多候选和多轮后处理链。

这是生成式改写模型，不是 AI 文本检测器。本次没有第三方检测率或盲评结果，不能据此声称“通过 AI 检测”。数字保护使用本地确定性算法，不增加第二次模型请求，也不保证人名、否定、动作和因果全部正确。

### 可复查的错误

1. 数字样本原文：“不是三万，是三千。”；温度 0.65 输出：“不是3万，是302。”。302 原本是后文房卡号码，被错误挪成了金额。
2. 悬疑样本原文先写推开仓库铁门、看到角落木箱；低温与强约束输出都从对白开始，删去这一段，还新增“林舟点点头”。
3. 数字样本的强约束输出删去“302 的房卡”和“赵川伸出的手停在半空”；低温输出保留房卡，但仍漏掉手部动作。
4. 已经克制的面条样本原样返回，说明“调用成功”不等于产生有用改进。

## 运行时复测

已在 Ollama 导入 F16 GGUF 并实测四个诊断样本，HTTP 全链路耗时 1.25–2.29 秒，生成速率约 48 tokens/s。首条含约 0.86 秒加载开销。悬疑样本仅剩 57%，仍缺失铁门与木箱；数字样本缺少末尾动作；克制原文没有变化。这些是未加数字保护的原始模型输出，不能直接等同于最终产品输出。

应用中的润色接口另加数字恢复与输出保护。明显删减或无法确认数字对应关系时，直接返回原选区及原因；空输出、截断或服务失败则返回错误，原稿均不改动。

导入模型后可用 Node.js 直接复测，无需 Python 业务后端：

```sh
node scripts/evaluate-polish.mjs
```

默认请求本机 `http://127.0.0.1:11434` 的 `moxu-polish:qwen3-1.7b`。脚本记录完整输入输出、耗时、加载耗时、生成速率、结束原因和缺失锚点，结果写入 `work/polish-ollama-results.json`。锚点仅是便于人工复核的线索，不是自动质量评分。

## 产品中的处理

- 单次润色，最多 3000 字符；更长文本请先选择段落。
- 默认本地 `moxu-polish:qwen3-1.7b`；旧 algorithm/hybrid 配置自动按本地模式读取，显式选择 llm 的配置保留。
- 对能可靠对应的金额、日期、编号、比例与单位恢复原值，预览中列出修正记录。
- 数字遗漏、新增、歧义或明显删减时保留整个原选区，说明原因；不按数字序号盲目替换。
- 超时、截断、空输出时返回错误并保留原稿；不偷偷切换模型。
- 成功结果进入差异预览，作者检查后确认；生成期间原稿改变则拒绝套用旧结果。
- 原有小说数据结构及 `com.wenshape`、存储键、API 路径保持兼容，产品显示名为“墨序 MoXu”。

## 数字保护回归验证

Java 回归测试共 258 项通过，其中数字保护专项 50 项。前端差异预览回归测试 9 项通过，前端生产构建通过。

覆盖范围包括中文/阿拉伯/全角数字、中文大写及廿卅卌、货币、正负号、小数、千分位、日期时间、房号、分数和百分比、单位变化、重复/遗漏/新增数字以及角色/动作上下文歧义。

例如“预算为3千元”被改成“预算为3万元”时，恢复为“3千元”；“他说不是三万，是三千”被改成“他说不是3万，是302”时，分别恢复两处原表达。上下文唯一时可以对应调序后的句子；无法唯一定位时保留整个原选区。检测到的数值表达和顺序均未变化时，允许普通文笔调整通过，不把普通同义改写一律退回原文。

应用接口测试另验证：润色请求不会保存章节；明显删减时返回原文及原因；空输入和超长输入会在调用模型前被拒绝。测试项目为独立临时项目，不覆盖用户原有章节。

数字保护版通过真实 Java → Ollama 接口复测四个诊断样本，耗时 1.11–2.05 秒。明显删减样本已返回原文和提示；其余样本分别原样返回或生成可预览候选。该轮未发生数字修复，数字错误的自动恢复由可控回归用例验证，不能把它描述成模型已经不再改错数字。完整记录在 `work/polish-api-current-results.json`。
